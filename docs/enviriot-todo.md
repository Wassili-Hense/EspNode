# TODO для Enviriot: лограммы на EspNode

EspNode программируется лограммой: блоки ввода-вывода и вычислений добавляются из контекстного меню,
пользовательский код — блок Func, диаграмма компилируется в байткод VM X13 (с float-командами) и
загружается по протоколу DevicePLC. Прошивка готова; ниже — что нужно в Enviriot (`D:\Projects\WebUI`).
Контракт прошивки — [plc-api.md](plc-api.md).

## 1. Объект `pa1` и DeviceLogram

EspNode регистрирует объект управления PLC как `pa1`, а не `pa0`, как X13: программы для EspNode (ввод-вывод
через `ConfigPin`, TWI 40–43, часы) и для X13 различаются, и Enviriot должен их различать. Протокол тот же,
что у `pa0` (DevicePLC).

- [x] Сделано (Enviriot `86370d1`): DevicePLC создаётся и для `pa1`, компилятор знает узел и отказывает в
  функциях другого (`UartInit` — только X13, `ConfigPin*`, `TwiBus*` — только EspNode). Теги X13
  (`var Op2;`) в программе для `pa1` — ошибка компиляции (`a6de46a`): ввод-вывод — блок `Pin`, см. п. 2.
- Новый тип устройства-лограммы, исполняемой на узле: из DevicePLC переходят build, run, start и stop;
  загрузка — как сейчас: `CRC_REQ` → `STOP_REQ` → блоки `WRITE_REQ` по 32 байта → `SET_STACK_REQ` →
  `START_REQ`.
- Собственные блоки DeviceLogram: ввод-вывод из описания устройства, вычислительные блоки, драйверы
  устройств TWI.
- [x] Описание устройства — [E1S10.xst](E1S10.xst) (`a6de46a`): поле `PLC` типа `MQTT-SN/E1S10`. Режимы
  сгруппированы вместе с пинами, на которых доступны; у режима — номер, направление для `Pin` и параметр
  (`opt`: диапазон или набор значений, обязательный `default`). Компилятор проверяет программу по нему,
  формат описан у `EP_Device` в Enviriot. Ставится загрузкой xst в IDE; после правки файла поднимать
  `ver`, иначе импорт молча пропустит его.

## 2. Блоки ввода-вывода

Конструктор блока настраивает пин (`ConfigPin2`, функция 31, попадает в init программы), цикл
выполняет ввод-вывод (`IN`/`OUT`). Параметры блока — константы времени компиляции.

- [x] Блоки DigitalInput … Counter из таблицы — один встроенный блок `Pin` (Enviriot `a6de46a`), режим
  выбирает, каким из них он работает: `var b = new Pin(pin, mode[, option])` — конструктор (`ConfigPin2`
  в init), `b.Tick()` — `IN`, `b.Tick(x)` — `OUT` (для выходов, ЦАП, ШИМ, счётчиков), выход блока —
  `b.value`. Пин, режим и параметр проверяются по описанию устройства. TwiBus, драйверы TWI и UartPort
  ещё впереди.

| Блок | Параметры (константы) | Конструктор | Цикл |
|---|---|---|---|
| DigitalInput | pin, подтяжка (нет / к питанию / к земле), инверсия, дребезг мс | `ConfigPin2(pin, IN…, debounce)` | выход = `IN pin` |
| DigitalOutput | pin, инверсия, открытый сток | `ConfigPin2(pin, OUT…, 0)` | `OUT pin` = вход |
| AnalogInput | pin, ослабление, период | `ConfigPin2(pin, ANALOG, atten)` | выход = `IN pin`, мВ, раз в период |
| AnalogOutput | pin (25/26) | `ConfigPin2(pin, DAC, 0)` | `OUT pin` = вход 0…255 |
| Pwm | pin, частота, инверсия | `ConfigPin2(pin, PWM…, freq)` | `OUT pin` = скважность 0…65535 |
| Counter | pin, фронты, фильтр нс | `ConfigPin2(pin, CNT_…, filter)` | выход = `IN pin`; вход сброса → `OUT pin, 0` |
| TwiBus | шина, SDA, SCL, кГц | два `ConfigPin` | — |
| драйверы TWI (датчики) | шина, адрес, период | — | `TwiControl`/`TwiStatus`/`TwiPutByte`/`TwiGetByte` (шина 0) или 40–43 (любая), код как у Func; обмен идёт в фоне, результат — в следующих циклах |
| UartPort | порт, TX, RX, DE, скорость, формат | `ConfigPin` на каждый пин | — |
| Modbus и т. п. (позже) | порт | — | `UartBytesToRead`/`UartGetByte`/`UartPutByte`; кадр — по паузе, как в X13 |

Номера режимов и смысл значений — таблица «Режимы пинов» в [plc-api.md](plc-api.md#режимы-пинов).
Ошибка настройки останавливает программу (`0x8A` — недопустимый пин или параметр, `0x89` — пин или
ресурс занят) с отчётом `STOP_RESP`: PC из отчёта стоит сопоставить с блоком и показать на диаграмме.

## 3. Компилятор (`DPLC/Compiler.cs`)

- Объявления в `LoadNativeFunctions`, все аргументы целые:

  | Имя | `Addr` | `pIn` | `pOut` | |
  |---|---|---|---|---|
  | `TwiControl`, `TwiStatus`, `TwiPutByte`, `TwiGetByte` | 1–4 | | | уже есть, шина 0 |
  | `NowSeconds`, `Today` | 9, 10 | | | уже есть |
  | `UartBytesToRead`, `UartGetByte`, `UartPutByte` | 21–23 | | | уже есть |
  | `ConfigPin1` | 30 | 2 | 0 | **убрать**: в прошивке функции 30 больше нет, вызов — `0x88` |
  | `ConfigPin2` | 31 | 3 | 0 | есть, только EspNode; в прошивке — `ConfigPin` |
  | `TwiBusControl` (bus, ctrl) | 40 | 2 | 0 | есть, только EspNode |
  | `TwiBusStatus` (bus) | 41 | 1 | 1 | есть, только EspNode |
  | `TwiBusPutByte` (bus, data) | 42 | 2 | 0 | есть, только EspNode |
  | `TwiBusGetByte` (bus) | 43 | 1 | 1 | есть, только EspNode |

  `UartInit` (20) на EspNode нет: порт открывает `ConfigPin`; компилятор для `pa1` его не принимает.
  Часы для `NowSeconds`/`Today` Enviriot выставляет через `0xFF07`, как узлам X13.
- [x] `IN`/`OUT` — через блок `Pin` (`a6de46a`): операнд кодируется как прежде (`Addr`:
  `place << 24 | type << 16 | base`), `base` — номер пина, `place` и `type` — 0. Теги X13 (`var Op2;`) на
  EspNode — ошибка компиляции.
- [x] Имена режимов и пинов — константы программы из описания устройства, только для EspNode:
  `ConfigPin2(4, PWM, 1000)`, `new Pin(PA5, OUT)`.

## 4. Компиляция DeviceLogram

- DeviceLogram хранится как граф экземпляров блоков и связей между их именованными входами и выходами. Каждый блок представляет экземпляр встроенного или пользовательского класса, имеющего конструктор и метод Tick.
- Конструкторы блоков объединяются в код инициализации программы. Методы Tick вызываются в порядке, определённом зависимостями графа. Все входные значения передаются в Tick как аргументы, а результаты передаются следующим блокам непосредственно через временные значения.
- Отдельный Merker для каждой связи не создаётся. Постоянная память выделяется только для состояния блоков, обратных связей, значений, доступных вне программы, и физического IO.
- Блок Func является встроенным типом блока. Его src используется как тело метода Tick и компилируется вместе со всей программой DeviceLogram.
- [x] Оптимизировать `Func.Tick` по аргументам. Было: у `Tick` всегда восемь параметров `A`…`H`, вызов клал
  неподключённые входы нулями (`LDI_0`) и после возврата снимал все восемь (`NIP`) — до 14 байт на каждый
  вызов. Сделано: `Tick` объявляет входы до последнего, который трогает `src` (по ссылкам в дереве разбора);
  связь на вход, которого `src` не трогает, — предупреждение, на его месте передаётся 0.
- Оптимизировать память программы. Сейчас `EP_Compiler` начинает каждую область кода — цикл программы,
  каждую функцию и метод — с адреса, кратного 32, и кладёт её отдельным куском `Hex` (`Compiler.cs`, раскладка
  перед сборкой `HexN`). Так удобно при заливке: кусок — целые блоки `WRITE_REQ` по 32 байта, у каждого свой
  CRC. Но каждая функция занимает минимум 32 байта, и на выравнивание уходит до 31 байта на функцию. Например,
  объединять классы в один кусок и выравнивать только границы кусков. Адреса для PC из `STOP_RESP`
  (`CodeLines`, `Element.Code`) берутся из итоговой раскладки, так что от упаковки не зависят.

## 5. Публикация переменных (авто-suppress)

Флаг `MQTT-SN.suppressed` появился из-за спама по шине. Для лограммы на узле флаг не нужен:
регистрировать на узле (`REGISTER M…`) только связи, которые используются вне устройства или имеют
`Logram.trace`. Остальные связи живут только в RAM программы: прошивка публикует только
зарегистрированные мерке́ры и только при изменении.

## 6. TWI

Объект `Ta0` (смешанный режим X13) на EspNode не нужен: TWI — только из программы (драйверы TWI —
блоки DeviceLogram).

## 7. Замечено в шлюзе при анализе

- `MsDevice.UpdateSuppressedInputs` считает маску по `_topics`; похоже, вызывается до регистрации
  входов, и маска уходит неполной — проверить порядок.
- `TWI.cs`: слишком длинный запрос навсегда занимает очередь TWI.
- `MsDevice.ReReg` оставляет запись в `_topics`.
